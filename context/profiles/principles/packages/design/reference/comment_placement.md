# Comment Placement

Comments explain why a non-obvious invariant exists; code structure
explains what the code does; extended rationale — history, design
alternatives, worked reasoning — belongs in context, not in the file.
Each artifact stays at its natural altitude: code carries invariants,
context carries decisions.

## The mechanical maxima

Comment bulk is enforced, not argued: inclusive maxima of 5
consecutive lines and 250 characters per block. Five consecutive
comment lines are valid, the sixth is an error; a 250-character
block is valid, the 251st character is an error. There is no
per-line maximum: readability is bounded by the block cap, not by
forcing mid-line wraps (operator amendment, 2026-09-16). Adjacent
comment forms that render as one prose block cannot bypass the
block maximum through delimiter changes or blank syntax-only
separators. The exact counting specification — delimiters,
indentation, newline bytes, doc prefixes, Unicode code points,
mixed line/block forms — is fixed by the repository's comment-policy
enforcement and its fixtures, which must agree across supported
languages (see Counting specification below).

Severity is authored, not fixed: a comment policy that is armed
without a severity value typically resolves to a warning, while an
`error` severity makes each surviving violation fail the run. Where a
repository arms the policy at `error`, the maxima gate — write to the
maxima rather than counting on advisory treatment, and check the
repo's authored value before assuming either posture.

## The four exemptions

Only four comment classes may exceed the maxima, by canonical name:

- **License header** — only a required license/copyright header
  qualifies; ordinary file prologues do not inherit the exemption by
  position.
- **Machine directive** — build tags, formatter/linter directives,
  generated markers, shebang-adjacent directives, and comparable
  machine-consumed forms qualify only to the extent their consumer
  requires.
- **Generated or vendored code** — a reliably detected generated or
  vendored file is foreign-authored and sits outside the
  author-comment policy wholesale: generator-owned comments and
  vendored third-party text are not author prose. Recognition is
  structural — a `linguist-generated` (set or `true`) attribute in
  `.gitattributes`, trusted index provenance, a standard generated
  file header in the leading comment region (the shared
  `genmark` grammar: "Code generated ... DO NOT EDIT.",
  `@generated`, `<auto-generated>`, "auto-generated by", "This
  file was auto-generated", or an uppercase "DO NOT EDIT" opening a
  line or beside "generated"), or a minified script asset (an
  ES-family file whose average physical line length carries the
  minified signature). A hand-authored file cannot gain the
  exemption from a near-miss marker: lowercase "do not edit" grants
  nothing, and a header below the first code line grants nothing.
- **Exported-API contract** — public documentation may exceed the
  limits only as far as needed to explain the callable contract, and
  only on contract-bearing API declarations; implementation narration
  does not inherit it, and comments on unexported declarations never
  qualify — an unexported doc comment must fit the maxima outright,
  section dividers included.

No exemption covers comments that merely restate the statement below
them: every exempt class still rejects obvious-syntax commentary when
the external constraint does not require the text.

## Repair guidance

When a diagnostic flags a comment:

1. If the comment states local behavior, replace it with
   intention-revealing code — a better name, a narrower function, a
   structure that makes the note unnecessary.
2. If the comment carries durable rationale (why the invariant exists,
   what breaks without it), keep at most a pointer-sized note and move
   the rationale to a specific context reference file (for example
   `reference/<topic>.md` in the repository's context module) that the
   diagnostic names — never a vague "see docs".
3. If the comment claims an exemption, check it against the four
   canonical classes; position, habit, and verbosity are not
   exemptions.

A worked reconciliation keeps count-bearing exported-API doc comments
while moving needless implementation narration into the reference
file.

## Counting specification

The counting engine's fixture corpus
(`testdata/`) is the executable spec.
Engine and fixtures must agree across Go, ES/TS,
Rust, and Python.

### The counting unit

Counts are Unicode code points, never bytes. A
tab counts as one. The BOM is stripped before
counting. CRLF is normalized so a newline adds
exactly one; the CR never counts.

### Line text

A counted line starts at its first non-
whitespace character. The delimiters `//`,
`///`, `//!`, `#`, `/*`, and `*/` count; the
indentation before them does not. `///` and
`//!` size as ordinary `//` lines.

### Blocks and merging

Line and block comments are separate block
kinds; a block comment is one block however many
lines it spans. Its total counts against the
250 maximum; the physical lines inside it are
counted only as that total's summands, with no
per-line bound.

"Consecutive" means adjacent comment lines with
no intervening code line; blank lines do not
break a run. Adjacent groups separated only by a
delimiter change, a blank comment-only line, or
a blank separator merge into one block. The most
common way an author meets the cap is the
divider: a `// ---` section divider merges with
the doc comment below it — a blank line between
them does not break the block — so divider+doc
groups must fit the maxima as one block.

A line of real code breaks the block; so does a
machine-directive line, which is not itself
counted. The exemption classifiers decide what
the directive's consumed text relieves.

### Language rulings

Python docstrings are string literals, not
comments: the engine never sizes them. Relief
for contract docstrings belongs to the
exported-API exemption, not to this counting.

Rust block comments nest: the scanner tracks
depth, and the outer block ends only at depth 0.

In ES/TS, template literals and strings that
contain comment delimiters are not comments. The
line-level scanner is acceptable here; the
checker may harden it later.

Doc prefixes (Go doc comments, Rust `///` and
`//!`, JSDoc `/**`) get no special sizing from
the counting engine; only an exemption class can
relieve them.
